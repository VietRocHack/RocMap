## 03:10 — Frontend polish: real desktop layout, bug fixes, footer, VietRocHack branding

User asked for the frontend (built mobile-first) to become properly responsive
on desktop, weird UI/UX quirks fixed, easier navigation, without changing its
"essential charm" - and to live-verify everything before shipping straight to
`main`.

**Root cause of the desktop gap**: `mediaqueries.css`'s `@media (max-width:
1200px)` block was the *only* place several classes were styled at all -
`.pop-up-container` (the white result card), `.info-title`, `.clarify-info`,
`.button-in-container`. Above 1200px, `App.css` had zero rules for them, so
real desktop monitors rendered the result screen and clarify-info section
completely unstyled (no card background, no button colors). Moved the
essential look for these into `App.css` as unconditional base rules; the
narrow-screen block still layers width-specific tweaks on top. Also added a
`min-width: 900px` block (in `mediaqueries.css`, and separately in
`WeatherRating.css` for its own selector - see the cross-file cascade-order
note below) that turns the result screen into a two-column CSS grid (image
left, info right, route bar spanning on top) and lays the weather-rating pills
out in a row instead of one long column, so wide screens actually use the
width instead of sitting as a narrow stretched mobile column. Verified via
`getBoundingClientRect()`/`getComputedStyle()` at 1280-1429px: grid areas
placed correctly, `.content`/`.result` centered at `max-width: 1100px`.

**Real bugs fixed** (found by driving the actual app, not just reading code):
- `showResultDiv` called `selectedEndLocation.id` with no guard - submitting
  with an incomplete form would throw. Added a `canSubmit` check and disabled
  the Submit button until start, door (if the hall has one), and destination
  are all set.
- `setShowResult(true)` ran synchronously right after starting the fetch, not
  in its `.then()` - the result screen would flash into view with stale/empty
  data before the response arrived, and a failed request left the user on a
  permanently broken empty result screen with only a bare `alert()`. Now shows
  a real loading state on the Submit button and an inline error message on
  failure, and only switches views once data actually arrives.
- Changing the "From" hall didn't reset the previously-picked door - a stale
  `startDoorId` from a different hall could get submitted silently. Typing in
  either field now invalidates that field's prior selection; the door
  `<select>` is now a controlled component so it visually resets too.
- Four `class=` (not `className=`) attributes in `App.js`, throwing a React
  console warning on every render.
- "Find another route" only reset `showResult` - form fields, selections, and
  results all stayed stale underneath. Now does a full reset.
- The empty "Start"/"Destination" labels rendered with nothing under them
  before anything was selected, reading as broken. Now show a muted "Not
  selected yet" placeholder (and a "Pick a door above" hint once a hall with
  doors is chosen but no door picked yet).
- The autocomplete dropdown visually collided with the clarify-info labels
  right below it (tight spacing, low z-index). Raised the dropdown's z-index
  and added breathing room.
- `box-shadow: ... rgba(0, 0, 0, 5)` - an alpha of 5 isn't valid CSS (browsers
  clamp it to 1); fixed to a real value.
- Weather rating radios used bare browser-default styling, clashing with the
  rest of the dark theme. Restyled as pill buttons matching the app's
  existing button language (same white-border-pill look as Explore
  Now/Submit) - hidden native radio, `:checked + span` drives the filled
  state, per explicit user ask ("fix up the default checkbox button to
  something a bit more fitting").
- **New two-column desktop layout exposed a second bug**: `.info`'s
  `width: 50%` had been dead code (irrelevant while `.pop-up-container` had no
  styling above 1200px at all); once the result card actually rendered at
  1280px+ in the new narrower grid column, that 50% crammed "Distance / ETA /
  ETA" into a strip too narrow for three columns, running the labels
  together. Fixed by matching mobile's existing `width: 100%` inside the new
  grid breakpoint. Caught by an actual screenshot after the grid change, not
  by only checking `getComputedStyle`.

**Cross-file CSS cascade hazard, avoided**: `WeatherRating.css` is imported
after `mediaqueries.css` in the module graph (via `App.js` -> `WeatherRating.js`
-> `WeatherRating.css`, which loads later than direct siblings `App.css`/
`mediaqueries.css`). An unconditional rule in `WeatherRating.css` would beat a
`@media` rule of equal specificity sitting earlier in `mediaqueries.css`,
regardless of which condition is "supposed" to win at a given width. Kept
`WeatherRating.css`'s own desktop override self-contained in the same file
instead of relying on `mediaqueries.css` to win the cascade for a selector it
doesn't actually own.

## 03:45 — Two bugs caught live on the actual deployed site, fixed and reshipped

User loaded the real `rocmap.vietrochack.com` (not just the local dev server)
after the previous entry's deploy and caught two things the earlier
verification missed:

1. **Form pill visibly overflowing its own border.** `.input-container` had
   a fixed `width: 500px` with no `flex-wrap`. With the door `<select>`
   visible (From input + door select up to 300px + To input - roughly
   740px minimum before padding), the row overflowed past the rounded
   border instead of wrapping, and since flex overflow spills past the end
   rather than redistributing, the whole cluster read as shifted off-center
   too. Fixed by changing to `width: auto; min-width: 500px; flex-wrap:
   wrap; margin: 0 auto`, so the pill grows to fit its content (or wraps
   cleanly to a second row) and stays centered either way. This case (From +
   door + To all visible at once) wasn't exercised in the earlier verification
   pass - all the prior screenshots happened to be taken either before a
   hall with doors was selected or after scrolling past that exact moment.
2. **Browser tab icon still showing the default Create React App logo.**
   The `<link rel="icon">` swap earlier only added `icon.svg` as an
   additional candidate; the actual default asset files
   (`favicon.ico`, `logo192.png`, `logo512.png`) were still sitting in
   `public/` and still referenced by `manifest.json` and the
   `apple-touch-icon` link, so any fallback path could still surface the old
   logo. Regenerated all of them from `icon.svg` using `npx sharp-cli` (PNGs)
   and `npx png-to-ico` (a real multi-resolution `.ico`, since sharp doesn't
   emit ICO), and added a proper `apple-touch-icon.png` (Apple doesn't
   support SVG there). No tool for this was already installed - resolved via
   one-off `npx` runs rather than adding new dependencies to the project.

Both verified two ways: `getBoundingClientRect()` against the real
`rocmap.vietrochack.com` (container width now 524px instead of overflowing
500px, properly centered), and a direct `curl` against the live URL
(bypassing any browser/CDN cache) confirming the served HTML actually
references the new build's hashed JS/CSS filenames, not a stale cached
version - the browser tool's own cached response briefly looked stale after
the deploy, which is what prompted the curl cross-check in the first place.

Lesson for next time: the deployed production URL is the real target,
`localhost` and prior screenshots aren't a substitute for actually loading
the live site again after each ship, especially for a layout-dependent
overflow bug that only shows up in one specific form state.
